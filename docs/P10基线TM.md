# P10 · 用官方译文做基线 TM（v2.25）

## 一、问题：官方译文被锁在两条路径里

v2.20 就把游戏本体的官方双语语料建了库（`official_tm.sqlite`，这台机器 164,357 对，
其中 onscreen 69,758 / 字幕 94,599）。但它的接入面很窄：

| 路径 | v2.24 之前 | 问题 |
|---|---|---|
| 资源模式（`.archive` / CR2W） | 加载时套用 | 正常 |
| 批量队列 | 加载时套用 | 正常 |
| **源码模式（`.reds` / `.lua`）** | **完全没套** | 最常用的一条路白丢 |
| **机翻前** | **完全不查** | 整句命中官方也要发给模型 |
| **写回后** | 不写记忆 | 手改的译文零复用 |

而且顺序是反的：先查机翻记忆，官方只补剩下的空位。同一句话如果记忆里躺着一条
早期机翻，官方译法永远用不上——「基线」名义上是底座，实际是补丁。

## 二、改法：三层查询栈 + 来源标注

```
手改(manual)  >  官方基线(official)  >  机翻记忆(machine)  >  模型
```

### 统一入口

新增 `src/baseline.py`，三条路径都调 `Api._baseline_fill(rows)`：

- `_do_load`（源码模式，以前没套）
- `_do_load_resource`（资源模式，以前顺序反了）
- `_run_translate`（机翻前，以前不查）

一次填充同时产出统计（`total / official / officialWeak / manual / memory / kept / left`），
状态栏、回执、导出都用这一份。

### 来源标记贯通到记忆层

`tm.Memory` 加了 `origin`：

```python
mem.put(src, tgt, text, origin="machine")   # 机翻
mem.put(src, tgt, text, origin="manual")    # 写回模组时记
mem.get_entry(src, tgt)                     # -> {"text", "origin"}
```

`put` 带优先级保护：已存在更高优先级的译文时，低优先级写入只刷新命中次数，**不覆盖**。

这一条修掉了一个隐性数据丢失：以前 `memory.put` 是无条件覆盖，机翻跑一遍就会把用户
手工改过的译文冲掉，而且没有任何提示。

### 机翻前先吃基线

`_run_translate` 里原来只有 `memory.get()`，现在先 `_baseline_fill`：

```python
bstat = self._baseline_fill([self.rows[i] for i in targets])
official_n = bstat["official"] + bstat["officialWeak"]
misses = [i for i in targets if not 译文]
```

只有 `misses` 才发模型。实测 AMM 的 156 条英文里 48 条直接命中官方，一次模型调用都不发。

### 目标语言守卫

官方语料是 en-us → zh-cn 单方向的。以前目标语言选日语/英语，中文照样被填进去。
现在 `baseline.load_official` 先判 `can_use_official(target_lang)`，不可用时返回原因：

- 目标语言不是「简体中文」→ `官方语料只有英文→简体中文，目标语言是「X」时不套用`
- 开关关掉 → `已关闭「加载时套用官方语料」`
- 库没建 → `还没有构建官方语料`

原因会原样出现在状态栏和设置页，不是静默降级。

## 三、关键发现：短词会漂移

第一版实现直接按「官方出现最多的译法」填，立刻炸出一批错译：

| 模组原文 | 官方给的 | 实际含义 | 结论 |
|---|---|---|---|
| `Pan` | 潘 | 平移（ImGui.DragFloat 的第三个轴） | ❌ 官方里是姓氏 |
| `Mark` | 马克 | 标记 | ❌ 官方里是人名 |
| `Title` | 歌名 | 标题 | ❌ 官方里指唱片曲目 |
| `Position` | 职位 | 位置 | ❌ 多义 |
| `Roll` | 滚动 | 翻滚 | ⚠️ |
| `Crosshair` | 准星 | 准星 | ✅ |
| `Off` | 关 | 关 | ✅ |
| `Close` | 关闭 | 关闭 | ✅ |

先试过用频次判别，不行：

| 词 | 频次 | 对不对 |
|---|---|---|
| `Mark` | 7 | ❌ |
| `Pan` | 2 | ❌ |
| `Crosshair` | 1 | ✅ |
| `Fog` | 1 | ✅ |

再试过用「译法分歧度」判别（同一 src 有几种 dst），也只覆盖一半：

- `Title` 有 3 种译法、`Position` 5 种、`Button` 2 种 → 能识别为歧义
- `Mark` / `Pan` 只有 **1 种**译法 → 识别不出来，它们不是歧义，是**语义漂移**

唯一站得住的分界是**词条长度**：

- 多词短语（≥2 词）且官方内部译法唯一 → 歧义极小，直接填
- 单词 → 照样填，但标 `official-weak`（界面「官方待核」，黄色条）

给用户一个开关（设置 → 「单词条的官方命中也算」，默认开）。关掉就只留稳的。

## 四、实测

```
Appearance Menu Mod  156 条英文（830 行）→ 官方稳 0 / 待核 48 / 待翻 108
Mod Configuration    281 条英文（523 行）→ 官方稳 1 / 待核  3 / 待翻 277
```

AMM 的 48 条基本都是 UI 单词：Close / Off / None / Default / Warning / Combat / Area /
Color / Yaw / Far / Nibbles。MCM 只有 4 条——框架文案几乎全是原创。

**结论要说清楚：官方基线的适用面是「短界面词」，不是「替掉机翻」。** 它省的是
最容易被机翻翻错、也最容易被玩家发现的那批词（`Off` 翻成「关闭」还是「关」）。

被 674 行「已有译文」挡住的那些，是模组自带的 zh-cn 语言包，不属于本次改动。

## 五、回归风险与自测

`tools/selftest.py` 新增 `check_baseline_layer()`，覆盖：

1. 官方优先于机翻记忆（`Off` 记忆里有「关闭」，官方给「关」→ 用官方）
2. 手改优先于官方（`Warning` 记忆里是手改的「警示语」→ 用手改）
3. 多词短语判为稳（`Street Cred` → `official`），单词判为待核（`Off` → `official-weak`）
4. `allow_weak=False` 时单词条不再由官方填
5. `memory.put` 不降级：手改先写，机翻后写，仍是手改
6. 目标语言守卫：`日本語` / `English` 返回 False，`简体中文` 返回 True
7. 端到端：两行都被官方命中时，`translate_batch` 调用次数 == 0

自测全绿，另外用真实模组跑过 `_do_load` 验证统计与状态栏文案。

## 六、边界

- **只对简体中文启用**。繁体同源但直出会造成简繁混排，暂时跳过。
- **单词条必然有不小比例的漂移**，这是语料性质决定的，不是实现问题。标「待核」而不是
  追求自动判别正确。
- **多词短语也可能错**（官方里的短语和模组语境不同），但实测概率低得多。
- 官方库是只读的 SQLite（`mode=ro`），重建语料不影响这份基线逻辑。
- 记忆条目里历史数据没有 `origin`，一律按 `machine` 算——所以官方基线能覆盖它们。
