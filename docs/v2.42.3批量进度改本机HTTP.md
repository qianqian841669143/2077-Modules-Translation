# v2.42.3 批量进度改走本机 HTTP（第三次 0xc0000005）

v2.42.2 把「后台线程推事件」改成了「前端轮询取事件」，仍然在第 54 个 mod 崩了。
这一页记第三次现场、为什么上一版没改对、以及这次换传送带的做法。

## 1. 第三次现场（v2.42.2）

| 项 | 值 |
|---|---|
| 启动 | 10:37:36 `v2.42.2` pid 22304 |
| 崩 | 10:43:16（约 5 分 40 秒，第 **54**/101 个 mod 刚 `start`） |
| 异常 | `0xc0000005` READ at `0xffffffffffffffff` |
| 模块 | `python314.dll +0x8eb82` |
| 转储 | `%LOCALAPPDATA%\CrashDumps\2077ModTranslator.exe.22304.dmp`（20.4 MB） |

`userdata/logs/crash.log` 这次抓到了完整栈（`faulthandler`，全线程）：

```
Windows fatal exception: access violation

Current thread 0x00006410 [Thread-1578 (_call)] (most recent call first):
  File "json\encoder.py", line 256 in iterencode
  File "json\encoder.py", line 202 in encode
  File "json\__init__.py", line 235 in dumps
  File "webview\util.py", line 256 in _call
  ...

Thread 0x000018b4 (most recent call first):
  File "threading.py", line 1011 in start
  File "webview\util.py", line 336 in js_bridge_call
  File "webview\platforms\edgechromium.py", line 251 in on_script_notify
  File "webview\platforms\winforms.py", line 808 in create
```

对一下源码就清楚是哪条路：

- `webview/util.py:247` `js_bridge_call`：**前端每调一次 Python API，pywebview 就新开一个线程**，
  在 `_call()` 里跑 `func(*args)`，然后
  `json.dumps(result)`（第 256 行）→ `window.evaluate_js(...)`（第 264 行）把结果写回界面。
- `json/encoder.py:256` 不是普通遍历，而是把参数递给 **C 加速器 `c_make_encoder`** 的那一行。
  崩在这里 = 崩在 C 层遍历对象图时，读到 `-1` 当指针。

所以这一次：崩的是**桥线程**，而且崩在「回写结果之前」。UI 线程当时正忙着
`Thread.start()` 起下一个桥线程。

## 2. 和上两次对照

| 次数 | 版本 | 异常地址（读） | 崩溃线程 | 当时在做什么 |
|---|---|---|---|---|
| 1 | v2.42.0 | `0xC0` | 批量工作线程 | 我在后台线程里 `evaluate_js` 推 `mb-item` |
| 2 | v2.42.0 | `0x10` | 同上 | 同上 |
| 3 | v2.42.2 | `0xffffffffffffffff` | pywebview 桥线程 `_call` | 即将 `evaluate_js` 回写 |

三次都不在 `try/except` 能碰到的层面（AV 是 C 层信号），地址一次比一次「野」，
但**都落在 pywebview 的 JS 桥上**，模块都是 `python314.dll`。

这推翻了 v2.42.2 的判断：「从后台线程调 `evaluate_js` 才有危险」不成立——
**只要经过桥（pythonnet 走进 WebView2 COM），高频往返就会踩**。
v2.42.2 只是把「后台推」换成「前端拉」，拉的时候照样过一次桥，而且
150 ms 一次，比原来推得还勤（一分钟 400 次）。第 3 次的栈正好抓在桥上。

## 3. 改法：批量事件换一条传送带

新增 `src/evbus.py`：一个**只监听 127.0.0.1 的只读事件端口**。

```
批量线程 ──append──> EventBus.q (deque)  ──GET /poll──> 前端 fetch（200 ms）
                                              ▲
                                   socket，不经过 WebView2 COM
```

- `EventBus.push()`：任意线程可调，只碰 `deque.append`（GIL 下原子）。
- `EventBus.start()`：`ThreadingHTTPServer(("127.0.0.1", 0))`，端口由系统分配，
  只提供 `GET /poll`，每次启动一个随机 token，路径/参数不对直接 404。
  响应带 `Access-Control-Allow-Origin: *` 与 `Connection: close`。
- `Api.__init__`：`self._bus = EventBus()`，`self._mb_q = self._bus.q`——
  兜底的 `batch_poll()` 与 HTTP 出口共用同一条 deque，谁先取谁拿。
- `batch_scan / batch_start` 不再新建 deque，改成 `self._bus.clear()`。
- `Api._boot_payload()` 多返回一个 `"pollUrl"`（起不来就是空串）。
- 前端 `_boot()` 存下 `_mbPollUrl`；`pollMbEvents()` 有它就走
  `fetch(url, {cache:"no-store"})`，200 ms 一次；`fetch` 抛错就清空 `_mbPollUrl`
  **退回原来的 `pywebview.api.batch_poll()`**，不会把面板卡死。

效果：一次 10 分钟的批量，桥调用从 1300+ 次降到 **0 次**（只在开面板、
点扫描、点开始时各一次）。

### 为什么不是「页面也走本地 HTTP」

`build_html()` 是故意用 `html=` 直接喂给 WebView2 的（见该函数注释：
免端口占用、更稳）。这次只把**事件**这条高频路径搬出去，页面加载方式不动。
实测 `html=` 载入的页面（`about:blank` 源）`fetch` 回环是通的：

```
href=about:blank
OK status=200 body={"ok": true, "events": [1,2,3], "running": false}
```

### 安全与副作用

- 只听 `127.0.0.1`，外部网卡连不上；端口随机；不带 token 一律 404；只读。
- 不占用固定端口，不需要管理员权限，**不会弹 Windows 防火墙**（回环不触发）。
- 进程退出时服务随守护线程一起结束，不留后台进程。

## 4. 验证

- `fetch` 可行性：真实 pywebview 窗口 + `html=` 页面 → `fetch` 回环 200，窗口正常退出。
- `evbus` 离线自检：3 条事件顺序取回、二次取空、`running` 跟随 `_mb_running`、
  坏 token/坏路径 404、塞 25000 条不炸（按 20000 上限丢最老）、`start()` 幂等（不换端口）。
- 全流程接线：`Api()._boot_payload()["pollUrl"]` 起得来，`_mb_push` 写进队列能被 HTTP 取走。
- 无头复现（不开窗口，同一份记忆/官方 TM 的副本）：60 个 mod 跑通、无崩溃。
- `tools/selftest.py` 全部通过；`node --check src/web/app.js` 通过。

## 5. 这次没动的地方

单模组的机翻 / 应用仍然走 `_emit` → `window.evaluate_js`（从工作线程）。
它们的调用次数远少于批量（一个 mod 几十条），目前没有崩过，先不动；
如果以后在单模组里也复发，同一条传送带可以直接复用：把 `_emit` 改成
`self._bus.push(obj)`，让前端常驻轮询即可（`onEvt` 已经能处理全部事件类型）。
