# v2.42.4：批量卡在第 25 个模组（提取正则预编译）

## 一、现场

第三次事故不是崩溃，是**卡死**。v2.42.3 换上本机 HTTP 之后没有 `0xc0000005`，
也没有新转储，但批量停在第 25 个 mod 上不动了。

| 项 | 值 |
|---|---|
| 启动 | 16:10:03，`2077ModTranslator.exe` pid 3416（父 22824 是 PyInstaller bootloader） |
| 断点 | 16:12:14 写完第 24 个 mod 的 `done`、写下第 25 个的 `start`，之后零输出 |
| 观察时长 | 到 16:23:49 已 **617 秒**无进展 |
| CPU | 720 秒 / 墙钟约 700 秒 = **单核 100%**，期间一直在涨 |
| 线程 | 一度 215 个，后来落到 11 个 |
| 磁盘 | `batch.log`、`run.jsonl`、`memory.json` 全部停在 16:12:14 |
| 网络 | 到 `127.0.0.1:11434` 的连接 **0 条**（还没走到翻译阶段） |
| 事件端口 | `127.0.0.1:50762` 在 LISTENING，但 `GET /poll` 三次探测全部超时 |

第 25 个 mod 是 `Enemies of Night City-8467-PL-Beta-1-8-8-Hotfix-1720272238`，
抓包时它的副本已经建好（17 个文件 / 4.4 MB，`.archive` 按配置跳过），
说明复制阶段完成，卡在**加载**。

## 二、把栈抓住

没有 py-spy 时只能看到「日志不写 + CPU 满」，分不清是在算还是在等。
装上 `py-spy 0.4.2` 之后直接读到线程栈（它不需要目标进程配合，也不受 GIL 影响）：

```
Thread 7336 (active+gil)
    search (re/__init__.py:177)
    _extract_lua (mod_text_engine.py:1283)
    extract_root_ex (mod_text_engine.py:1666)
    _do_load (web_app.py:773)
    run_one (mod_batch.py:225)
    run (mod_batch.py:288)
    work (web_app.py:1769)
```

`re/__init__.py:177` 就是 `return _compile(pattern, flags).search(string)`。
`--native` 进一步显示它停在 `_compile` 内部（`PyUnicodeWriter_Finish`），
也就是**在重新编译正则，不是在匹配**。

连续四次采样（跨 25 秒以上），局部的 `lit` 对象地址始终是 `0x2987a4750d0`、
`head` 始终是同一段文本 —— 循环一次都没往前走。

那一行是：

```python
head = text[max(0, lit.start - 1500):lit.start]
m = re.search(r"""([A-Za-z_]\w*)\s*=\s*\{[^{}]*$""", head)
```

## 三、离线复现：同一份文件只要 6 秒

用同一份 `Base.lua`（1,116,215 字节 / 1,116,039 字符 / 20857 个字面量）单独跑：

| 测法 | 耗时 |
|---|---|
| `scan_source`（分词） | 0.07 s |
| 第 3 阶段正则遍历全部 20857 个字面量 | 4.24 s（最坏单次 0.5 ms） |
| `_extract_lua` 完整跑 | **6.18 s** |
| 单次 `re.search(字面量, head)` | 0.17 ms |
| 强制 `re.purge()` 后单次 | 0.21 ms |
| 卡住的那个 head 单独测 | **0.2 ms** |

复现不出「11 分钟」。也就是说：**这段代码本身不该卡，但它在真实进程里确实卡了**，
而且是单次调用卡住（`lit` 不推进），不是「整体慢」。

## 四、为什么是这段代码

不管那次异常慢的确切触发条件是什么（多线程下 `re._cache` 被冲掉、每次重新编译，
是最合理的解释；`--native` 栈正好落在 `_compile` 里），这段代码有三个结构性问题：

1. **pattern 是字符串字面量**。`re.search("...", head)` 每次都要先查
   `re._cache`（`_MAXCACHE = 512`），这个缓存是**全局共享**的。批量进程里
   一度有 215 个线程（见下节），任何地方编译新 pattern 都可能把这一项挤掉，
   于是每次调用都重新编译。
2. **窗口太大**。每个字面量都切 1500 字符再扫一遍，20857 次 = 3100 万字符，
   正常也要 4.24 秒，占整个提取的 69%。
3. **没有剪枝**。正则要求 `name = {`，但绝大多数窗口里连 `{` 都没有，
   却照样进正则引擎。

## 五、215 个线程是怎么回事

v2.42.3 的设想是「前端用 `fetch` 从只读端口取事件，不碰 pywebview 桥」。
但卡死之后 GIL 被提取线程占住，`ThreadingHTTPServer` 的 accept 线程拿不到 GIL，
`fetch` 全部超时；前端 `pollMbEvents` 的 `catch` 里会 `_mbPollUrl = ""` 退回
`pywebview.api.batch_poll()`，而桥每调一次都要新开线程再 `evaluate_js` ——
线程于是堆到 215 个，进一步抢 GIL。

**这是卡死的后果，不是原因，但它会把「卡一下」放大成「彻底没救」。**

## 六、改了什么

1. `src/mod_text_engine.py`
   - 新增模块级 `ASSIGN_TAIL_RE` / `LIST_HEAD_RE` / `_ASSIGN_VAR_RE` /
     `_ASSIGN_LINE_RE`，四个「逐字面量 / 逐调用」的热路径正则全部预编译；
   - 第 2 阶段加 `"=" not in head` 剪枝，第 3 阶段加 `"{" not in head or "=" not in head`
     剪枝（正则必然要求这两个字符，剪枝完全等价）；
   - `_assigned_var` / `_assign_target` 同样加 `=` 剪枝。
2. `src/web/app.js`
   - `pollMbEvents` 的 `catch` 不再立刻退回桥，改为原地重试；连续失败 300 次
     （约 60 秒）才停轮询；
   - 只有 `fetch` 返回非 200（token/路径过期）才退回桥；
   - 新增 `showStall()`：连续失败 3 秒起在面板上显示橙色提示。
3. `src/web/index.html` / `src/web/style.css`：新增 `#q-stall` 提示行与 `.hint.stall`。
4. `src/appconfig.py` / `assets/version_info.txt`：版本升到 v2.42.4。

## 八、遗留

- **GIL 被 C 代码占住时，Python 层做不了超时**：`threading.Timer`、
  `faulthandler.dump_traceback_later` 都需要 GIL。所以这次没有加「看门狗强行
  掐断单个 mod」，只能在面板上告诉用户「卡住了、关掉重开、已完成的会跳过」。
  真要硬超时，得把加载放到子进程里用 `join(timeout)` + `terminate()`，改动太大，
  这次不做。
- 单模组的 `_emit` 仍然走 `evaluate_js`（见 backlog 相应条目），调用量比批量少
  一个量级，这次没动。
- 这次是**卡死**，与 v2.42.0/2.42.2 的两次 `0xc0000005` 不是同一类问题；
  v2.42.3 的 HTTP 通道改动继续保留。
