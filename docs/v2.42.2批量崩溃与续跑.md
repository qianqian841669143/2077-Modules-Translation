# v2.42.2 批量崩溃（0xc0000005）与续跑

2026-11-01 上午，批量翻译连跑两次都在中途整窗消失。这一页记现场、判定过程和改法；
详细待办在 `docs/backlog.md`。

## 1. 现场

事件查看器里两条记录（不是被谁关掉的，是进程自己崩了）：

| 时间 | 进程 | 异常 | 模块 |
|---|---|---|---|
| 10:17:15 | PID 0x3B14 | `0xc0000005`（AV，读 0xC0） | `python314.dll +0x4D209` |
| 10:26:37 | PID 0x3DB0 | `0xc0000005`（AV，读 0x10） | `python314.dll +0x98100` |

`%LOCALAPPDATA%\CrashDumps` 里留下对应的两个 dmp（21 MB / 20 MB）。
两次故障地址不同、都是「读一个接近 NULL 的地址」，说明不是一个固定分支写错，
而是**指针/线程状态被踩**。

从 10:26 那个 dmp 里能捞到崩溃前最后一条事件（堆里的 JS 脚本原文）：

```js
eval("window.__evt && window.__evt({\"type\": \"mb-item\", \"phase\": \"start\",
      \"index\": 27, \"total\": 101, \"name\": \"Garage Core - CHTxCHS …\"})")
```

也就是 **101 个里的第 28 个刚开始** 就死了。`userdata/batch/out` 里正好躺着
27～28 个副本，与之一致；`out` 里最后建的是 `GTA Travel …`（10:26:36）。

## 2. 判定

- 不是 Python 异常：`0xc0000005` 是访问冲突，`try/except` 抓不到，
  窗口直接消失，`apply.log` 之类一行都不留。
- 崩溃点落在 `evaluate_js`：脚本正文就在堆里，而且这是 `_emit` 唯一做的事。
- 为什么平时没事：`_emit` 是**从后台线程**调 `window.evaluate_js`，
  那是跨到 WebView2 的 UI 线程（COM）去执行脚本。单次调用几乎不会出问题，
  批量连着推几十个 mod（`mb-item` 每个 mod 两条 + 扫描每 5 个一条）才踩中概率。
  与「故障地址两次不同」也吻合：踩的是线程状态，不是固定代码。
- 崩溃发生在 **开始第 28 个 mod 那一刻**，说明当时线程正在推 `mb-item start`。

## 3. 改法

### 3.1 事件改成前端轮询（`src/web_app.py` / `src/web/app.js`）

后台线程只碰 Python 对象，不碰 COM：

```
批量线程 ──append──> Api._mb_q (deque)  <──popleft── batch_poll() <──150ms── JS 定时器
```

- `Api._mb_push(obj)`：append + 顺手写日志/续跑记录。`MB.Ctx(on_event=self._mb_push)`。
- `Api.batch_poll(limit=300)`：一次最多取 300 条，返回 `{events, running}`。
  `running` 同时算上扫描中（`_mb_scanning`），否则预扫一开始前端就把轮询停了。
- JS：`window.__evt` 拆成 `onEvt(e)`（兼容原来的推送路径），
  新增 `startMbPoll / stopMbPoll / pollMbEvents`；`openQueue / scanQueue /
  startQueue` 里开轮询，`batch_poll` 返回「没事件且没在跑」时自动停。
- 其余流程（单模组机翻、应用）仍走原来的 `_emit` 推送，没有改动。

### 3.2 崩了不用重头再来

`userdata/batch/run.jsonl`，一行一个 mod：

```json
{"key": "…", "ok": true, "dst": "…/batch/out/xxx", "rows": 268, "todo": 147, "applied": 147, "failed": 0, "at": "…"}
```

- 行首有一条 `{"__sig": …}`：参数指纹 = staging 目录 + 归档开关 + 跳过素材开关 +
  目标语言 + 模型。换了任何一个，旧记录整份作废（否则会把别的参数跑出来的产物当已完成）。
- 重跑时跳过 `ok=true` **且产物目录还在**的条目；`batch_start` 返回 `cached` 数量，
  界面显示「（跳过上次已完成的 N 个）」。
- 半行（崩溃时正在写）解析失败就跳过，不影响其余记录。
- 「清空输出」会连 `run.jsonl` 一起删，所以清空之后再跑就是完整重跑。

### 3.3 下次崩了要能查

- `userdata/logs/crash.log`：`faulthandler.enable(all_threads=True)`。
  C 层访问冲突时把**所有线程**的 Python 栈写进去，直接看到是哪一行。
  文件头每次启动写一行 `==== 时间 版本 pid ====`。
- `userdata/logs/batch.log`：`start 28/101 名字` / `done 名字 ok=… rows=… applied=…`，
  超过 512 KB 自动滚成 `.old`。就算 faulthandler 也没抓到，也能知道断在第几个 mod。
- `sys.excepthook` / `threading.excepthook` 也写进 `crash.log`。

## 4. 验证

- `tools/selftest.py`：全部通过。
- 离线自检（不开窗口）：事件进 deque → `batch_poll` 取回顺序正确；
  扫描中 `running=true`、都停了变 false；续跑记录写/读；参数变了作废；
  产物目录被删不算完成；半行不影响解析；`crash.log` / `batch.log` 落盘。
- `node --check src/web/app.js` 通过。
