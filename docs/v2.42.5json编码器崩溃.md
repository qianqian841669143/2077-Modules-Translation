# v2.42.5：批量闪退（json C 编码器访问违例）

## 一、现场

v2.42.4 之后批量跑到第 44 个 mod（`Redscript Config Framework`）时**闪退**，
窗口直接消失，没有「未响应」那 5 秒的过渡。

| 项 | 值 |
|---|---|
| 时间 | 16:36:44（WER 1000） |
| 异常 | `0xc0000005`，出错偏移 `python314.dll+0x5283f` |
| 进程 | pid 21708，v2.42.4 |
| 转储 | `%LOCALAPPDATA%\CrashDumps\2077ModTranslator.exe.21708.dmp`（20,281,404 B） |
| 断点 | `batch.log` 停在 `start 44/77`（16:36:21），`run.jsonl` 68 行 |
| 桌面 | 16:36:49 另有一条 WER 1001（`APPCRASH`，类型 4） |

与上一次（v2.42.4 之前的 AppHang）的区别：**AppHang 是窗口卡住被 Windows 关掉，
APPCRASH 是进程自己崩了**。这次是后者。

## 二、崩溃栈

`crash.log` 里 `faulthandler` 抓到的完整栈：

```
Windows fatal exception: access violation
Current thread 0x00000fb0 [Thread-126 (work)]:
  File "json\encoder.py", line 389 in _iterencode_dict
  File "json\encoder.py", line 413 in _iterencode_dict
  File "json\encoder.py", line 413 in _iterencode_dict
  File "json\encoder.py", line 444 in _iterencode
  File "json\__init__.py", line 181 in dump
  File "tm.py", line 60 in save
  File "web_app.py", line 2246 in _run_translate
  File "mod_batch.py", line 244 in run_one
  File "mod_batch.py", line 288 in run
  File "web_app.py", line 1769 in work
```

对照 `json/encoder.py` 源码：

```python
389:            yield _encoder(key)
...
413:                    yield from chunks
```

`ensure_ascii=False` 时 `_encoder` 就是 `encode_basestring`，而它在模块里被绑定为
**C 实现** `c_encode_basestring`。也就是说：崩溃发生在 C 层的字符串编码函数里，
不是在我们的数据上。

## 三、这是第三次栽在同一处

| 次 | 版本 | 崩溃位置 | 触发路径 |
|---|---|---|---|
| 1 | v2.42.0 | `json/encoder.py:256`（`c_make_encoder(...)` 的参数行） | 后台线程 `evaluate_js` 推事件 |
| 2 | v2.42.0 | `json/encoder.py:256` | 同上 |
| 3 | v2.42.4 | `json/encoder.py:389`（`yield _encoder(key)` → `c_encode_basestring`） | `tm.save()` 在批量线程里写盘 |

三次的共性很清楚：**都死在 CPython `_json` 的 C 编码器里**，只是入口不同
（`c_make_encoder` vs `c_encode_basestring`）。第一次被误判成 pywebview 桥的问题，
v2.42.2/2.42.3 把桥整个绕开了，结果第三次证明**桥只是恰好经过 json**。

## 四、排除过的可能

**并发写 TM？** 不是。`spawn_worker()` 里 `w._memory = self._memory_store` 确实让
主实例和批量 worker 共享同一个 `Memory`，但批量运行时只有 work 线程在 `put`/`save`。
做了一个实验：7,000,000 次 `put` + 400 次并发 `save`（另一个线程同时在改字典，
且会触发 `_trim()` 整体替换 `entries`），**零异常、不用杀进程**。
`_trim()` 用 `dict(items[...])` 换掉 `self.entries` 也不危险——遍历中的旧 dict 有引用
计数保护。

**数据里有坏键？** 不是。`Memory._key()` 固定返回 sha1 hexdigest，必然是 str；
`_iterencode_dict` 在没有 `sort_keys` 时直接 `yield _encoder(key)`，传进去的就是这个 str。

所以只剩一个解释：**CPython 的 `_json` C 编码器在 3.14.8 上会访问违例**。
这类崩溃在 Python 层接不住（`try/except` 无效、`faulthandler` 只能留栈），
唯一可行的做法是绕开。

## 五、改了什么

1. `src/appconfig.py`（所有模块都会 import 它）顶部加补丁：

   ```python
   import json.encoder as _jenc
   _jenc.c_make_encoder = None
   _jenc.encode_basestring = _jenc.py_encode_basestring
   _jenc.encode_basestring_ascii = _jenc.py_encode_basestring_ascii
   ```

   - `c_make_encoder = None`：`json.dumps` 不再用 C 的 one-shot 编码器；
   - 换掉 `encode_basestring(_ascii)`：`json.dump`（流式，本来就走 Python 的
     `_make_iterencode`）在编码每个 key/值时会调用它，这是第 3 次崩溃的直接入口。

2. `src/tm.py`
   - `Memory.__init__` 加 `self._last_save = 0.0`；
   - `save()` 加 3 秒节流：`_run_translate` 原来每补翻一条就 `save()` 一次，
     绕开 C 之后会反复序列化同一份字典；`force=True` 时不受限。

## 七、验证

| 项 | 结果 |
|---|---|
| 补丁生效 | `c_make_encoder = None`、`encode_basestring = py_encode_basestring`、`encode_basestring_ascii = py_encode_basestring_ascii` |
| `tools/selftest.py` | 全部通过 |
| 无头批量 40 个 mod | 12.2 s 跑完，无崩溃 |
| v2.42.5 exe | 13,518,820 B / `2.42.5.0`，启动后子进程监听 `127.0.0.1:60691` |

## 八、遗留

- 这只是**绕开**，不是修好 CPython。若哪天 `json.load` 的 C 解码器也出现同类
  违例，同样的思路处理（`json.decoder` 也有 c 版 scanner，可以换成纯 Python）。
- 纯 Python 编码器慢 5 倍左右，但绝对值仍是 0.1 秒级，暂时不需要再优化；
  真要更快，可以把 TM 改成 sqlite 增量写，不在本次范围。
- 前两次崩溃（v2.42.0）被归因成 pywebview 桥，v2.42.2/2.42.3 的改动（前端轮询、
  本机 HTTP）**不是白做**——它们确实消掉了桥上的调用，只是没消掉 json；
  这三版的结论不冲突，见 `docs/v2.42.4提取正则卡死.md` 与 `backlog.md`。
