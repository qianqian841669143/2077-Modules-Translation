# P6 分层提取：语言包不再独占一次加载

## 现象

用户拿 *Much Better Contracts 2.1*（Vortex 装的那个目录）反馈：

> 只翻译了语言包内文件，并未提取翻译 .lua 内等设置相关文本

具体到界面：模组设置菜单（CET → Mods → Much Better Contracts）里的
`Enabled` / `Enable Debug Log` / `Difficulty` / `T2 Boss Health x` 这些开关名和说明
还是英文，而模组的剧情、档位文本（走 Codeware Provider 语言包）已经翻好了。

## 定位

先确认这不是提取器的问题。直接对单个文件跑提取：

```
nativeSettingsUI.lua → 29 条（显示名称 10 / 描述 9 / 分类 3 / 选项文本 7）
```

一切正常。再看整目录：

```
iter_source_files → 9 个 .lua + 190 个 .reds，一个不少
extract_root_ex   → bin/x64/.../*.lua 有行
```

所以问题在**调度**，不在提取。`web_app.Api._do_load()` 的流程是：

```python
if opts["localeFirst"]:
    files = locale_pack.detect(root)          # 找到 6 组 Provider 配对
    if opts["providerPair"]:
        if pairs:
            ...
            if lrows:
                return {...}                   # <-- 这里直接返回了
    if files:
        if srcs:
            if lrows:
                return {...}                   # <-- 这里也是
data, meta = E.extract_root_ex(...)            # 只有没有语言包时才走到
```

只要模组里有一套语言包，源码层就永远跑不到。MBC 恰好三种文本源都有：

| 位置 | 内容 | 旧行为 |
|---|---|---|
| `r6/scripts/.../Localization/*English.reds` | 剧情、档位、操作名（1,539 条） | ✅ 提取 |
| `bin/x64/.../MuchBetterContracts/nativeSettingsUI.lua` | 设置界面（29 条） | ❌ 消失 |
| `r6/scripts/.../Gigs/*.reds` | `@runtimeProperty` 设置项、通知文本 | ❌ 消失 |

这是个通用问题：**语言包和设置界面是两套机制**，Provider/Codeware 管前者，
CET `nativeSettings` + `@runtimeProperty` 管后者，同时使用非常常见。

## 改法一：两层合并

把语言包层的结果存下来，源码层照跑，最后拼成一张表：

```python
loc_rows, loc_meta = 语言包层(...)          # 不再 return
consumed = {r["file"] for r in loc_rows} | {r["target"] for r in loc_rows if r["target"]}
data, meta = E.extract_root_ex(root, exclude_rels=consumed | 目标语言文件, ...)
rows = loc_rows + src_rows
```

- 每行带 `layer: "locale" | "source"`，状态栏显示「语言包 N 行 / 设置与源码 M 行」。
- 语言包文件按**相对路径**从源码层排除（连目标语言文件一起），
  所以不会出现「同一个 `BoardEnglish.reds` 被提取两遍」。
- `mode` 仍然是 `provider` / `locale` / `content`，前端提示语不变。

## 改法二：REDscript 证据分级

合并之后暴露出第二个问题：源码层 3,052 条里大部分是**内部诊断字符串**。

```redscript
this.m_issue = "native cycle changed outside the selected run";
MBCInfo("BigPete", "all targets neutralized cycle=" + ToString(this.m_cycle));
```

旧逻辑是「任何 `is_translatable()` 为真的字面量都算界面文本」（`_extract_reds` 的
`else` 分支），逻辑重的模组必然灌水。现在按**证据**分级：

| 证据 | 判定 | 默认 |
|---|---|---|
| `@runtimeProperty("ModSettings...", "...")` | 该字段对应的类型 | 收 |
| `this.Text("key", "value")` 的 value | 界面文本 | 收 |
| `StrReplaceAll` 目标语言项 | 界面文本 | 收 |
| 赋值目标是 `title` / `message` / `label` / `localizedName` … | 对应设置类型 | 收 |
| 赋值目标是 `m_*` / `s_*`，或名字含 `issue`/`error`/`log`/`state`… | 内部文本 | **不收** |
| 出现在 `Log`/`Print`/`MBCInfo`/`MBCWarn` 等日志调用里 | 内部文本 | **不收** |
| 其它 | 长句文本 | 受「长句兜底」控制 |

两个细节：

1. **日志包装函数的识别**。模组普遍自己封一层 `MBCInfo(channel, message)`，
   名字不带 `Log` 前缀。所以除了 `^log|^print|^warn…` 前缀，还会把名字拆成词片段
   （`MBCInfo → [mbc, info]`、`lastMessage → [last, message]`），片段里出现
   `log/dbg/trace/warn/error/info` 就按日志处理；但 `ShowInfoDialog`、`CreateErrorBox`
   这种以 UI 动词开头的名字会排除在外。
2. **拼接片段**。`"Board: enabled="`、`" player=unavailable"` 这类是拼给日志看的，
   形如 `word=` 的一律不算句子（只对「没有位置证据」的兜底档生效，
   有证据的界面文本不受影响）。
3. **记录名不是文本**。`StringToName("MBC-Operation-Misfire-Stage" + ...)` 只是拿字符串
   去查 TweakDB，翻它会把查表打断。`StringToName` / `StringToEnum` / `ToName` /
   `ToCName` 这类调用的字符串参数一律跳过。

## 新增开关

| 开关 | 默认 | 作用 |
|---|---|---|
| .lua 设置文本 | 开 | 扫 CET `.lua` |
| 长句兜底 | 开 | 收「没有位置证据但像句子」的文本（长句文本） |
| 调试文本 | **关** | 连内部状态 / 日志字符串一起收 |

## 实测（Much Better Contracts 2.1）

| 开关组合 | 语言包 | 源码/设置 | 合计 |
|---|---|---|---|
| 默认 | 1,539 | 1,926 | 3,465 |
| 关掉长句兜底 | 1,539 | **287** | 1,826 |
| 打开调试文本 | 1,539 | 3,262 | 4,801 |

旧行为是 **1,539 / 0**（设置文本整片缺失）。

关掉长句兜底后的 287 条里，`nativeSettingsUI.lua` 占 29 条：

```
L37  分类     Much Better Contracts
L38  分类     General
L39  分类     Debug
L44  显示名称  Enabled
L54  显示名称  Enable Debug Log
L54  描述     Master toggle for debug output. When off, only ERROR-level emits.
L70  显示名称  Difficulty
L75  显示名称  T2 Boss Health x
L75  描述     Health multiplier for Tier 2 nemesis bosses.
...
```

回填验证（临时副本上跑，不碰用户目录）：**29/29 命中，0 失败**，
引号类型保持，`GetLocalizedTextByKey("MBC-Settings-EnabledHint")` 这类 key 不会被误改。

## 已知取舍

- **物品名要不要翻**。`BoardOptionalRecipeData.reds` 里 1,435 条
  `"Militech Ajax Raptor Common"` 是配方条目的显示名，玩家确实会看到；但它们和
  游戏本体物品译名是否一致没有保证，机翻反而可能对不上号。现在归入「长句文本」，
  由用户用筛选器自行决定收不收，工具不替用户拍板。
- **源文件模式的批量队列**仍未接入。批量队列目前只跑归档（资源模式），
  源码文件仍是一次一个模组。
- 语言包层的「未配对 Provider」仍只提示不处理，与 v2.19 一致。

## 回归

`tools\selftest.py` 新增两项：

1. `check_reds_evidence_tiers` —— 构造一个含 `m_issue` / `LogChannel` /
   `showInfo` / 数据表名称的 `.reds`，断言三种档位的收录行为，
   以及 `loose=False` / `trace=True` 的差异。
2. `check_layered_extraction` —— 若本机装了 Much Better Contracts，直接调
   `Api._do_load`，断言：`mode == "provider"`、两层都非空、`nativeSettingsUI.lua`
   的四个关键行类型正确、内部诊断字符串不在结果里、同一文件只出现在一层。

外加原有的真实模组用例保持通过（`Anti-Tracking Breach` 67 条不变）。
